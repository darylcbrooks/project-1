### [Project 27 - Conducting Log Analysis with Splunk](https://youtu.be/Lfv3efnpk2I)

In this project, I’ll be demonstrating how the Splunk SIEM tool can be used to investigate rogue processes through log aggregation and parsing. Splunk is a Security Information and Event Management (SIEM) solution used for searching, monitoring, and analyzing machine‑generated data, primarily for IT operations, security, and observability.

In the following scenario, an alert has been generated by my Splunk SIEM indicating that a rogue process within my enterprise may be enumerating a local user group. The suspected malicious process may be masquerading as the essential Windows process “explorer.exe”.

## Searching for explorer.exe’s Parent Process

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2001.png)

To access Splunk, I open my web browser and navigate to where it’s being hosted (http://192.168.1.8:8000).

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2002.png)

Next, I need to access the list of logs captured by Splunk. To do so, I click the “Apps” menu at the top of the window and choose the “Search & Reporting” option.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2003.png)

The following screen presents a search bar where I can query specific logs according to different variables (filename, log type, etc.). I begin by broadening my search, changing the time parameter at the end of the search bar from “Last 24” to “All time.” As implied, this expands the search to include all logs captured throughout Splunk’s operational lifecycle. I then enter the following string into the search bar to query all system monitoring and Windows event logs relevant to the “explorer.exe” process:
Add source=”xmlwineventlog:microsoft-windows-sysmon/operational”.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2004.png)

This returns a list of logs, and the leftmost pane contains menus that allow me to parse specific details. I scroll down and click the “parent_process” menu. The parent process appears to be “ghghghg.exe,” which is highly likely to be a malicious file. The odd naming convention and the fact that it is an executable make this suspicious.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2005.png)

I then return to the search bar, replace “explorer.exe” with “ghghghg.exe,” and run the search again.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2006.png)

This returns system monitoring and Windows event logs related to the suspicious executable. In the leftmost pane, I select the “CommandLine” option, which reveals that changes were made to the power configuration settings — likely an attempt to implement persistence via scheduled tasks. Disabling hibernate and standby timeouts may indicate an effort to keep the system from entering low-power modes, possibly to ensure continuous operation or avoid detection.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2007.png)

Returning to the search query, I replace “ghghghg.exe” with “powercfg.exe” to search for the scheduled task(s) that may be altering the device’s power settings.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2008.png)

Clicking the “process_exec” menu shows that powercfg.exe is associated with another process named conhost.exe. Conhost.exe is a legitimate Windows process that manages command-line tools like Command Prompt and PowerShell. This supports the theory that someone used the Windows CLI to create a scheduled task that triggers powercfg.exe.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2009.png)

Clicking the “parent_process_path” menu provides further evidence that powercfg.exe is responsible for triggering the suspicious ghghghg.exe file.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2010.png)

Next, I replace “powercfg.exe” in the search query with “cmd” to search for specific Windows commands that might confirm the existence of a scheduled task responsible for maintaining the altered power settings.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2011.png)

I click the “CommandLine” menu again, and the third and fourth events immediately stand out. In the third event, I can see that the cmd utility was used to create a directory named “fgfdgd.” In the fourth event, a scheduled task named “Nafifas” was created to run an executable file called fgfdgd.exe every one minute. This repetitive execution may be what’s causing the system’s power settings to allow the device to stay on indefinitely.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2012.png)

With the discovery of this file, I replace “cmd” in the search query with “fgfdgd.exe” to find all logs related to it.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2013.png)

By clicking the “parent_process” menu, the second event shows where fgfdgd.exe is created by the scheduled task, and the third event shows where the file is copied into the “fgfdgd” subdirectory.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2014.png)

Finally, I want to confirm the relationship between “ghghghg.exe” and “fgfdgd.exe.” To do so, I replace “fgfdgd.exe” with “(fgfdgd.exe OR ghghghg.exe)” in the search query.

![Image](https://github.com/darylcbrooks/project-1/blob/project-27/Project%2027%20-%20Step%2015.png)

Clicking the “parent_process” menu reveals the same events observed in the previous searches. However, now I can see that after the successful execution of “fgfdgd.exe,” the “ghghghg.exe” process appears. This indicates that “fgfdgd.exe” is responsible for triggering the “ghghghg.exe” process.

## Conclusion

Malware often disguises itself as explorer.exe to evade detection, blend in with legitimate system processes, and maintain persistence. If an attacker remains on a system long enough, they can enumerate local group memberships to identify privileged accounts for escalation. By monitoring unusual activity linked to user accounts, I improved the enterprise’s ability to detect and respond to security threats before they escalate. Log analysis and proactive security monitoring help safeguard an organization’s infrastructure.
